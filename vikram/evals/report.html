Reading guide

What the benchmark tells you

This starter suite gives an initial signal. Better observed scores can come from an agent change, sampling variation, or imperfect grading.

Pass@1 and pass@k

Pass@1 estimates success in one fresh attempt. Pass@k estimates at least one success in k independent attempts. Each starts with no earlier answers or grader feedback. Pass@k does not identify which answer to choose.

Thinking level

A model setting, such as off/on or low/medium/high. Supported values come from Ollama’s model metadata. Each is a separate benchmark configuration. Unspecified model defaults and untested levels are labeled explicitly.

Eval suite

A fixed set of cases, success criteria, and judge settings. Agent changes stay on the same timeline. Changing the cases or grading starts a separate section, so unrelated scores are not mixed.

Configuration and repeat

A configuration includes model, thinking, prompt, runtime/tool code, dependencies, harness versions, and generation settings. The table averages complete repeat runs equally; latest scores are also shown.

Baseline, latest, and best

Progress cards compare the latest complete score to the first complete score for each metric. Best is the highest observed score. The optional comparison panel lets you choose another baseline.

Case and attempt

A case is one task with explicit success criteria. An attempt is one fresh response. Scores average cases equally. At least k scored attempts per case are needed for pass@k.

Objective check / judge

Objective checks compare answers with expected text or structure. A local Ollama judge checks written rubrics after all models finish generating. Judge model and thinking settings stay fixed within a suite. A judge can make mistakes or favor its own model; graphs show objective and judged scores separately.

Unavailable / not run

Errors and interrupted attempts are unscored, not wrong answers. An overall score needs every case complete. “Not run” means a supported thinking level has no run for that configuration. Neither is zero.

Percentage points

60% to 70% is +10 percentage points. History shows changes from the previous run in that suite. Comparisons can involve different models or thinking levels; they are observed differences, not causal proof.

Controlled comparison

Keep cases, grading, sample budget, and the working tree fixed when comparing models or thinking levels. The comparison panel lists recorded differences. Experiment labels describe intent without hiding other runs.

Provenance

Fingerprints record code and settings without saving their content. Legacy records lack some fingerprints and thinking metadata. External services, environment variables, non-Python resources, and mutable model tags are not fully captured.

Evaluation time / uncertainty

Time per attempt is recorded run duration divided by its attempt count, including grading and setup overhead. Waiting for other configurations is excluded. It is not model-only latency. Small samples and timing variation limit conclusions; no statistical significance is claimed.

The calculation, with an example

pass@k = 1 − C(n − c, k) / C(n, k), where n is attempts, c is passes, and 1 ≤ k ≤ n. C counts combinations and is zero when its first argument is smaller than k. Case scores are averaged equally.

Two passes in five attempts give pass@1 = 40%, pass@3 = 90%, and pass@5 = 100%. A sample’s 100% score is not a guarantee.

Offline report. Metrics and configuration metadata only; no prompts, answers, thinking traces, judge explanations, source content, or credentials. Times use your browser’s timezone. Rebuild to include new runs.
